# Larascraper v3 — Design spec (breaking major)

Working spec for the v3 rewrite. **v3 is a breaking major.** Existing v2 scrapers
(`handle()` + `$this->crawler` + `run()->data`) must be migrated. v2 stays published
and functional; v3 is opt-in (`"edulazaro/larascraper": "^3"`). External impact is
negligible (0 Packagist dependents, 3 stars at time of writing); the only real
consumer to migrate is the crowd.legal project.

> **Status (jul 2026):** v3 is implemented in the package working tree (uncommitted,
> 48 tests green). This spec reflects the design AS IMPLEMENTED. Pending: the user tags
> it, then crowd's scrapers migrate (CENDOJ last).

---

## 1. Motivation

v2 mixes two concerns inside `handle()`:

- **Fetching** (get the page / the file), and
- **Parsing** (extract data from it).

And v2's `ScraperResponse` is really a **request** response (HTTP `status`, `html`,
`cookies`) wearing a scraper name.

v3 separates the two, with concrete responsibilities:

- **Request layer** → `RequestResponse` (HTTP: status, html, file, cookies). Internal.
- **Scraper layer** → the `Scraper` orchestrates and decides scrape success **by
  content**; the `Crawler` parses; `run()` returns a `ScraperResponse` (data +
  scrape-level outcome).

**Key insight: HTTP 200 != scrape succeeded.** A 200 can be a captcha / block / "no
results" page. Scrape success is content-based and lives in the scraper, not in the
HTTP status. Mixing the HTTP status in as "success" was the root confusion of v2.

---

## 2. Responsibilities

| Piece | Responsibility |
|---|---|
| **`Scraper`** | Fetch + orchestration (retries, proxy, `$this->scrape()`). ALL scraper logic, encapsulated, no leaks to the caller. Decides scrape success by content. |
| **`Crawler`** | Parse HTML (`$this->filter(...)`). Reusable, independent of how it was fetched. |
| **`CapturedFile`** | A downloaded file (a PDF). `->text()`, `->vision()`, `->bytes()`, `->save()`. |
| **`RequestResponse`** | The HTTP request result: `status`, `error`, `html`, `file`, `contentType`, `cookies`. Produced by the Runner. Internal to the scraper. |
| **`ScraperResponse`** | The scraper's result, minimal: `data`, `success` (scrape-level), `error` (scrape-level). No `request` — the HTTP layer stays internal. Returned by `run()`. |

One-line map:
- `RequestResponse` = "what the server returned" (HTTP).
- `Scraper` = orchestrate, retry, judge validity.
- `Crawler` = parse.
- `ScraperResponse` = "what the scraper got" (data + scrape outcome).

---

## 3. The `Scraper`

You extend `Scraper`. `$this->scrape($url)` starts a fetch chain (a builder).
`handle()` is the default method (triggered by `run()`); you can add more methods for
other operations of the same site. Retries / proxy / config live on the class.

```php
use EduLazaro\Larascraper\Scraper;
use EduLazaro\Larascraper\Support\ScraperResponse;

class BikeSite extends Scraper
{
    protected int $tries = 3;                 // reintentos, encapsulados aqui

    // Default method: triggered by BikeSite::run(...)
    protected function handle(string $url): ScraperResponse
    {
        return $this->scrape($url)
            ->crawl(BikeCrawler::class)        // parsing in a Crawler class
            ->run();
    }

    // A single bike (HTML -> Crawler)
    public function find(int $id): ScraperResponse
    {
        return $this->scrape("https://tienda.com/bikes/{$id}")
            ->crawl(BikeCrawler::class)
            ->run();
    }

    // Quick inline extraction (no Crawler class)
    public function names(): array
    {
        return $this->scrape('https://tienda.com/bikes')
            ->crawl('.bike-card h3')
            ->texts();
    }

    // A PDF datasheet (file -> text / vision)
    public function datasheet(int $id): string
    {
        $file = $this->scrape("https://tienda.com/bikes/{$id}")
            ->click('a.datasheet')
            ->capture()
            ->file();                          // runs the chain, returns the CapturedFile

        return $file->text() ?: $file->vision('ai');   // text, or OCR if scanned
    }
}
```

Inside the scraper, the HTTP layer is reachable via **`$this->request`** (a
`RequestResponse`): `$this->request->status`, `$this->request->cookies`. Low-level, for
when you genuinely need it.

The `crawler` is NOT set on the Scraper anymore (that was v2). Parsing lives in the
`Crawler` (or the inline `->crawl('selector')` terminal).

`handle()` may return the crawler's `ScraperResponse` (as above), a raw value, or
`$this->fail('code')` — `run()` normalizes any of them into a `ScraperResponse`
(see section 8). It never has to build one by hand.

---

## 4. The chain and its terminals

`$this->scrape($url)` returns a builder. Fetch/browser steps are the same as v2:
`->click()`, `->submit()`, `->capture()`, `->gotoAttr()`, `->solveCaptcha()`,
`->when()`, `->repeatUntil()`, `->driver('http')`, `->proxy()`, etc.

Terminals decide what you get back:

| Terminal | Returns |
|---|---|
| `->crawl(FooCrawler::class)->run()` | `ScraperResponse` (data = what the Crawler produced) |
| `->crawl('css selector')->text()` | `string` (first match, runs at once) |
| `->crawl('css selector')->texts()` | `string[]` (all matches) |
| `->capture()->file()` | `CapturedFile` (then `->text()` / `->vision()`) |
| `->run()` | `ScraperResponse` (no crawler; raw data/html) |

---

## 5. The `Crawler`

Parsing, separate from fetching. Reusable: it parses a page regardless of how it was
fetched.

```php
use EduLazaro\Larascraper\Crawler;

class BikeCrawler extends Crawler
{
    protected function handle(): array
    {
        return [
            'name'  => $this->filter('h1')->text(),      // Symfony DomCrawler over the fetched HTML
            'price' => $this->filter('.price')->text(),
        ];
    }
}
```

The Crawler can also signal a **scrape-level failure** (e.g. expected selector missing
-> the page is a block/captcha) by throwing `ScrapeException`, which becomes
`ScraperResponse->success = false` + `->error`.

---

## 6. `CapturedFile` (carried over from 2.3, unchanged)

A captured file (a PDF). Same API and engines as 2.3.

```php
$file->text($engine = 'gs')      // text layer: gs | poppler | smalot
$file->vision($engine = 'ai')    // OCR: ai | tesseract  (rasterize with pdftoppm)
$file->bytes()                   // raw bytes
$file->save($path)               // write to disk, return path
$file->contentType()             // 'application/pdf'
$file->size()                    // bytes
```

Config (`ai` engine): `config/larascraper.php` (`openai_key`, `vision_model`,
`vision_lang`, `vision_dpi`) or `OPENAI_API_KEY`. Each engine fails with a clear
message if its tool (`gs` / `pdftotext` / `pdftoppm` / `tesseract`) is missing.

## 7. `RequestResponse` (internal, the HTTP layer)

Produced by the Runner (browser or http). Accessible inside the scraper as
`$this->request`, and attached to a `RequestException` when the request fails.

```
status:       int            // HTTP status (200, 404, 503...)
error:        ?string        // network / HTTP error message, null otherwise
html:         string         // the fetched HTML
file:         ?CapturedFile  // a captured binary (from capture()/submit())
contentType:  ?string
cookies:      array          // Set-Cookie as name => value
```

This is what v2 called `ScraperResponse`. In v3 it is correctly named: it is the
**request's** response.

---

## 8. `ScraperResponse` (returned by `run()`, the scraper layer)

Intentionally minimal — the scrape result only:

```
data:     mixed      // what handle() / the Crawler produced
success:  bool       // did the SCRAPE succeed (content-based, scraper-decided). Default true.
error:    ?string    // scrape-level error code: 'captcha', 'no_results', ...  NOT an HTTP code
```

**No `request` field.** The HTTP layer (`RequestResponse`) is internal: read it inside
`handle()` as `$this->request`, and on a request failure from
`RequestException->response`. It is deliberately not surfaced on the scrape result,
which stays about content only. `success`/`error` are the scraper's judgement, not HTTP:
a `status = 200` can still be `success = false, error = 'captcha'`.

### What `handle()` returns — `run()` normalizes it

`run()` and `with()->run()` ALWAYS return a `ScraperResponse`; `handle()` does not have
to build one:

- **a raw value** (string, array, ...) -> wrapped as `ScraperResponse(data: $value, success: true)`.
- **a `ScraperResponse`** (from `crawl(Class)->run()`, or `$this->fail()` / `$this->ok()`) -> passed through unchanged.
- **`return $this->fail('no_text')`** -> `ScraperResponse(success: false, error: 'no_text')`. No `new`, no `throw`.
- **`throw new ScrapeException('no_text')`** -> caught by `run()` and folded into the same failed response. Equivalent to `fail()`, for failures raised deep in a Crawler or nested code.
- **`return $this->ok($data)`** -> explicit success (same as returning `$data` raw; provided for symmetry).

```php
protected function handle(string $url): array
{
    $text = trim($this->scrape($url)->capture()->file()->text());

    if ($text === '') {
        return $this->fail('no_text');   // success=false, error='no_text'
    }

    return ['text' => $text];            // success=true, data=['text' => ...]
}
```

## 9. Failure model — one exception at the caller, content failure as data

Two layers, but the caller only ever catches ONE exception:

- **Request-level failure** (network down, or a status treated as failure after the
  bounded retries) -> `RequestException`, carrying the `RequestResponse`
  (`$e->response->status`). This is the only exception that reaches the caller.
- **Scrape-level failure** (captcha, no results, wrong document) -> comes back as
  `success = false` + `error`, NOT an exception. It is produced by
  `return $this->fail('code')`, or by a `ScrapeException` thrown inside a Crawler or
  `handle()` (both are caught and folded into a failed `ScraperResponse`).

Caller:

```php
try {
    $r = BikeSite::run($url);            // always a ScraperResponse
    if (! $r->success) {
        // content failure: $r->error is 'captcha' / 'no_results' / ...
    }
    $data = $r->data;
} catch (RequestException $e) {
    // request layer only -> $e->response->status (retry on 503, skip on 404, ...)
}
```

Why content failure is data and not an exception: it is an *expected* outcome of
scraping (pages block, layouts change), so the caller branches on `$r->success` rather
than a `try/catch`. A genuine transport failure (`RequestException`) is the exceptional
case. Need HTTP facts (status/cookies) on success? They are on `$this->request` inside
`handle()`; fold whatever you need into `data`.

## 10. Parameter passing (consistent with `laractions`)

Same pair as `edulazaro/laractions`, so the two packages feel identical:

- **`run(...$params)`** -> args go to **`handle()`** (positional, named, or an
  associative array mapped by name to handle()'s parameters; a single array to a
  single array-typed param = "attribute bag").
- **`with(...$params)`** -> injects into the scraper's **properties** by name
  (chainable), then you call `run()`.
- **Constructor** -> for dependencies/config; via a `make(...)` factory or the
  container. `with()` covers property state, so constructor injection is only for real
  deps.

```php
ReportScraper::run($url);                    // -> handle(string $url)
ReportScraper::run(['url' => $url, 'id' => 5]); // mapped by name to handle(...)
ReportScraper::with(url: $url)->run();       // set $this->url, then run()
ReportScraper::with(['url' => $url])->run(); // array -> properties by name
```

Reference implementation to mirror: `laractions` `Action::run()` (reflection over
handle params, positional/named/bag) and `Action::with()` (reflection over properties).

## 11. Breaking changes (v2 -> v3)

- `handle()` role changes: it now **calls** `$this->scrape(...)` (was: called AFTER the
  fetch, receiving `$this->crawler`).
- Parsing moves out of `handle()` into `Crawler` classes (or the inline
  `->crawl('selector')` terminal).
- `run()` returns a `ScraperResponse` with **scrape-level** success/error (was:
  HTTP-level fields).
- v2 `ScraperResponse` (HTTP-shaped) is **split**: `RequestResponse` (HTTP, internal) +
  `ScraperResponse` (scrape). The scrape result is `{data, success, error}` only — HTTP
  facts (`$result->status`) are no longer on it; read them via `$this->request` inside
  `handle()`, or `RequestException->response`.
- `run()` no longer requires `handle()` to build a `ScraperResponse`: a raw return is
  wrapped as `data`, `$this->fail('code')` marks a failure, and a `ScrapeException`
  thrown in `handle()` / a Crawler is caught and folded into `success = false` (it no
  longer propagates to the caller).
- 2.3 PDF: `$this->file->text()` inside `handle()` becomes the chain form
  `->capture()->file()->text()`.
- `capture()` / `submit()` / `submitAndCapture` (deprecated) stay as chain actions.

---

## 12. What carries over from 2.3 (no rework)

- The chain actions **`capture()`** and **`submit()`** (Node `scraper.cjs` + PHP
  `BuildsActions`), and the deprecated `submitAndCapture`.
- **`CapturedFile`** — same class, same engines (gs/poppler/smalot/tesseract/ai),
  reached now via the `->file()` terminal instead of `$this->file`.
- The response recorder in `scraper.cjs` (for `capture()`).
